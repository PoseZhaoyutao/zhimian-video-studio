核心问题
切换用户时，对当前项目有什么影响？
用户 A
→
用户 B
系统正在服务用户 A，突然切换到用户 B
影响发生在三个层次，逐层分析
① 上下文隔离
② KV Cache 失效
③ 项目状态重新召回
🛡️

上下文隔离

用户A的对话历史不能进入用户B的上下文窗口，这是安全基线。

出错 = 数据泄漏

❄️

KV Cache 失效

前缀不同，缓存全部miss，必须重建，冷启动延迟。

首token延迟 50ms → 800ms+

📦

项目状态重召

项目上下文需从记忆库重新召回，暖启动 vs 冷启动。

记忆库为空 = 上下文丢失

影响 ① 上下文隔离
用户 A 的历史不进入用户 B 的窗口
● 用户 A 的上下文
system: 你是A的助手
A: 帮我改登录页
AI: 已修改LoginForm.jsx
A: 再加个记住密码
隔离墙
● 用户 B 的上下文
system: 你是B的助手
B: 查一下销售数据
AI: Q3同比增长12%
B: 按地区拆分
安全基线：切换瞬间必须清空当前上下文，重新构建用户 B 的上下文。出错即数据泄漏。工程上按用户 ID 隔离上下文会话，物理不共享。
08 / 12
影响 ② KV Cache 失效
前缀不同，缓存全部失效，必须重建

● 同用户续聊

prefix: [sys, A1, AI1, A2, AI2] → append A3
前缀不变，追加新 token
首 token 延迟：低（~50ms） · 命中复用

● 切换到用户 B

prefix: [sysB, B1, AI1] → 全新前缀
前缀完全不同，全部 miss
首 token 延迟：高（~800ms+） · 冷启动
❄️
冷启动延迟：切换用户后，第一个 token 的生成时间显著升高，因为模型要重新处理整个上下文前缀。工程优化是按用户 ID 做 prefix cache 分桶，但跨用户复用基本不可能。

结论：多人协作的 AI 系统必须显式管理项目状态——用独立的项目记忆区或结构化状态对象，而非依赖隐式对话历史

工程设计原则
切换用户的四条设计原则
1

上下文按用户隔离

物理不共享，按用户 ID 独立会话。防止数据泄漏。

物理隔离
2

KV Cache 按用户分桶

同用户内复用，跨用户隔离。prefix cache 按 user_id 分桶。

分桶复用
3

项目状态显式持久化

不依赖隐式对话历史。用独立项目记忆区或结构化状态对象。

显式持久化
4

切换用户主动预热

预加载用户 B 的偏好和最近项目，减少冷启动延迟。

主动预热
做到这四条，切换用户的体验损失主要就是首 token 延迟，其他都能掩盖
